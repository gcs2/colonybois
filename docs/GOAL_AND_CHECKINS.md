# Positive production goal and check-ins

23 September 2026. The existing Codex goal remains active and is sufficient to continue. This document clarifies execution; it does not replace the app's goal or declare any milestone complete.

## Goal wording for a future migration

Build Colonybois into a cohesive, polished, original creepy-cute spiritual successor to Spore's base Space Stage. Make personal spaceship exploration, discovery, collection, trade, diplomacy, colonization, planet manipulation, progression and conflict work together as one satisfying game. Account for every base Space Stage feature and explicitly record user-approved adaptations or deferrals before claiming parity. Preserve mouse-first interaction, optional arrows/numpad controls, meaningful resource costs and danger, expressive aliens, responsive animation, professional readable interfaces, and reviewed sound, music and guidance.

Work toward playable end-to-end milestones, starting with one persistent ship exploring three worlds, carrying and trading cargo, contacting a civilization, earning and purchasing an upgrade, facing a consequential challenge, and saving/loading the complete journey. Integrate presentation and feedback into these milestones. Fix pressing defects promptly; keep bounded visual iterations from repeatedly displacing new playable capability. Preserve rejected-art feedback as acceptance constraints, without making criticism the organizing purpose of development.

Use TASK_BOARD.md as the authoritative work queue and SPACE_STAGE_TARGET.md as the feature contract. Keep status evidence-based: distinguish plans, isolated prototypes, integrated behavior, verified builds and player-approved results. Maintain small validated GitHub checkpoints with remote verification. Respect the current engine, aggregate simulation, licensing and purchase-approval constraints. After baseline parity and core-loop review, develop the broader content, synergies, living ancestor story, human Sol scenario and other tracked ambitions. Explicitly deferred scope never counts as delivered parity.

Completion requires the agreed feature inventory to be accounted for, integrated playable sessions, appropriate persistence/performance/input checks and player review of fun and presentation. Automated tests alone cannot establish AAA quality.

## Status check-ins

TASK_BOARD.md remains the entry point; no second production queue is introduced. When asked for a check-in, report:

- Current milestone, next concrete action and blockers.
- Changes since the previous checkpoint, using existing task IDs and playable evidence.
- Feature coverage by non-overlapping owning category, distinguishing isolated implementation from integrated completion and presentation acceptance. Explain the denominator and uncertainty for any percentage.
- Code/content statistics dated to an exact commit, with counting rules. Assets or planet records are not necessarily approved assets or visitable worlds.
- Forecast ranges with assumptions, recalibrated from completed milestones rather than token counts or lines of code.
- Latest playable build, validation limits and verified remote backup hash.

Detailed breakdowns may support existing board tasks. Do not maintain independently competing status values. The preliminary status report and parity TSV are research drafts; neither supersedes the board or proves an exhaustive retail-item audit.

## Unattended operation

The app goal was checked and is active. Goals support continued work across turns, subject to runtime availability, usage limits, approval requirements and blockers. An active goal does not guarantee uninterrupted execution or zero risk. Keep the app and machine available for local work. This project does not authorize purchases, unrelated system changes, bypassing access restrictions or weakening permissions. Use the existing scoped permissions and verified backups.
